# BB-0003 - Roles as a Separate Entity

## Status

Implemented

## Date

2026-11-04

## Problem

`assignees.role` was a free-text `String(100)` column:

- every typo produced a new "role", and the UI only offered a hardcoded
  `ROLES` list inside `AssigneesPage.tsx` that could not be edited;
- roles could not be renamed, sorted or validated in one place;
- the same text was duplicated in every assignee row instead of referencing a
  dictionary.

## Goal

Introduce a `Role` entity with full CRUD, link assignees through a foreign key
and keep the rest of the product unchanged:

- roles are managed in the UI (page `Исполнители` -> tab `Роли`);
- an assignee has zero or one role;
- renaming a role renames it for every assignee that uses it;
- a role that still has assignees cannot be deleted;
- existing free-text roles are migrated into the dictionary.

## Changes

### 1. Database - `backend/app/models.py`, `backend/alembic/versions/0004_roles.py`

- new table `roles` (`id`, unique `name` `String(255)`, `created_at`);
- `assignees.role` (`String(100)`) replaced by `assignees.role_id`
  (`Integer`, `ForeignKey("roles.id")`, nullable);
- `Role.assignees` / `Assignee.role` relationships, both `lazy="selectin"`
  (same pattern as `Task.assignees`: no N+1 and usable after `db.refresh()`).

Migration `0004` (`down_revision = "0003"`):

| Step | Upgrade | Downgrade |
|---|---|---|
| 1 | `create_table("roles")` | `add_column("assignees", "role")` |
| 2 | `add_column("assignees", "role_id")` with FK | `UPDATE assignees SET role = (SELECT LEFT(name, 100) FROM roles WHERE roles.id = assignees.role_id)` |
| 3 | `INSERT INTO roles SELECT DISTINCT TRIM(role) FROM assignees WHERE role IS NOT NULL AND TRIM(role) <> ''` | `drop_column("assignees", "role_id")` |
| 4 | `UPDATE assignees SET role_id = (SELECT id FROM roles WHERE roles.name = TRIM(assignees.role))` | `drop_table("roles")` |
| 5 | seed `AssigneeRole.ALL` only when `roles` is empty | - |
| 6 | `drop_column("assignees", "role")` | - |

The correlated-subquery form is used instead of `UPDATE ... FROM` so the same
statement works on PostgreSQL and SQLite (the tests use SQLite).

### 2. Schemas - `backend/app/schemas.py`

- new `RoleCreate` (`name`, 1..255), `RoleUpdate` (`name` optional) and
  `RoleRead` (`id`, `name`, `created_at`);
- `AssigneeCreate.role: str` -> `AssigneeCreate.role_id: int | None`;
- `AssigneeUpdate.role: str | None` -> `AssigneeUpdate.role_id: int | None`
  (explicit `null` clears the role, `model_fields_set` still separates
  "unchanged" from "clear");
- `AssigneeOut.role` is a nested `RoleRead | None` instead of a string.

### 3. API - `backend/app/api/roles.py` (new), `backend/app/api/assignees.py`,
`backend/app/main.py`

New router `/api/roles` (`tags=["roles"]`), same style as `/api/tags`:

| Method | Path | Behaviour |
|---|---|---|
| `GET` | `/api/roles` | list, ordered by `name` |
| `POST` | `/api/roles` | `201`; `400 Role with this name already exists` |
| `PATCH` | `/api/roles/{id}` | rename; `404` unknown, `400` duplicate name |
| `DELETE` | `/api/roles/{id}` | `204`; `400 Cannot delete role with assigned assignees` |

- `api/assignees.py`: `_check_role()` raises `400 Role not found` for an
  unknown `role_id` on create and update;
- `main.py`: `roles.router` registered right after `assignees.router`.

### 4. Frontend - `frontend/src`

- `types.ts`: new `Role` interface, `Assignee.role?: Role | null`;
- `api.ts`: `listRoles` / `createRole` / `updateRole` / `deleteRole`,
  `role_id` in `createAssignee` / `updateAssignee`;
- `pages/AssigneesPage.tsx`:
  - two tabs (`Сотрудники` / `Роли`) driven by local state, the route did not
    change;
  - roles tab: table with the name and compact inline-SVG edit/delete buttons
    (`title` + `aria-label`), `Новая роль` button and a modal with a single
    name field (save is disabled while the name is blank);
  - staff tab: role `<select>` with a `Без роли` option replaces the old
    `datalist`, the hardcoded `ROLES` constant is gone;
  - assignees and roles are loaded together through `Promise.all`, every
    mutation re-runs `load()` so a rename is visible in both tabs;
- `styles.css`: `.tabs` / `.tab` / `.tab.active` / `.icon-btn`;
- `translations.ts`: `assignees.tabStaff`, `assignees.tabRoles`,
  `assignees.noRole`, `roles.name`, `roles.new`, `roles.empty` (ru/en).

### 5. Tests - `backend/tests`

- `conftest.py`: new `role` fixture, the `assignee` fixture now sends
  `role_id`;
- `test_tasks.py`: `{"name": "Petr", "role": "QA"}` -> `{"name": "Petr"}`;
- new `test_roles.py` (12 cases): create/list ordering, duplicate name, empty
  name validation, rename propagates to assignees, rename to an existing name,
  rename unknown role, delete with assignees, delete a free role, delete
  unknown role, assignee with unknown `role_id`, assignee without a role,
  clearing a role with `role_id: null`.

### 6. Spec and README - `spec.md`, `README.md`

- new `Assignees and roles` section in `spec.md`;
- `Role management` added to `Main Features` in `README.md`.

## Contract changes (breaking)

| Before | After |
|---|---|
| `AssigneeCreate.role: str \| null` | `AssigneeCreate.role_id: int \| null` |
| `AssigneeUpdate.role: str \| null` | `AssigneeUpdate.role_id: int \| null` |
| `AssigneeOut.role: str \| null` | `AssigneeOut.role: RoleRead \| null` |

There are no external clients and the frontend was updated in the same
change. `report_service`, `task_service` and the Telegram intake only use
assignee names, so they were not touched.

## Migrations

`backend/alembic/versions/0004_roles.py` creates `roles`, backfills it from the
distinct trimmed values of `assignees.role`, rewrites `assignees.role_id`
through a correlated sub-select, seeds the previously hardcoded list only when
the dictionary is empty and finally drops `assignees.role`.

## Known limitations

- Downgrade truncates role names longer than 100 characters (the old column was
  `String(100)`) and loses roles that have no assignees.
- Role names are compared case-sensitively: `QA` and `qa` are two roles.
- `enums.AssigneeRole` is kept only as the seeding source for the default list.
- Deleting a role does not detach or reassign its assignees; the request is
  rejected instead (as specified in the ticket).
- The roles tab is local UI state, so deep links like `/assignees?tab=roles`
  are not supported.
