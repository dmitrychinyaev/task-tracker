# BB-0002 - Multiple Assignees per Task

## Status

Implemented

## Date

2026-11-04

## Problem

A task could reference exactly one assignee through the `tasks.assignee_id`
column:

- real work is often shared by several people, and the single column forced
  either duplicated tasks or informal notes in the description;
- the API exposed `assignee_id` / `assignee` in every task payload, so any
  attempt to support more people would have been a breaking change anyway;
- reports, the Telegram intake and the assignee delete-guard all depended on
  the single-column model.

## Goal

Replace the one-to-many relation with a many-to-many one without changing the
rest of the product:

- a task can have zero, one or many assignees;
- filtering by assignee still works (`GET /api/tasks?assignee_id=X`);
- existing single-assignee data survives the migration;
- the UI lets the user pick several assignees and shows all of them.

## Changes

### 1. Database - `backend/app/models.py`, `backend/alembic/versions/0003_task_assignees.py`

- new association table `task_assignees` (`task_id`, `assignee_id`, composite
  primary key, both `ON DELETE CASCADE`);
- `Task.assignee_id` column and `Task.assignee` relationship removed;
- new `Task.assignees` relationship: `secondary=task_assignees`,
  `back_populates="tasks"`, `lazy="selectin"`, `order_by="Assignee.id"`
  (stable order, no N+1, usable after `db.refresh()`);
- `Assignee.tasks` now uses the same secondary table.

Migration `0003` (`down_revision = "0002"`):

| Step | Upgrade | Downgrade |
|---|---|---|
| 1 | `create_table("task_assignees")` | `add_column("tasks", "assignee_id")` |
| 2 | `INSERT INTO task_assignees (task_id, assignee_id) SELECT id, assignee_id FROM tasks WHERE assignee_id IS NOT NULL` | `UPDATE tasks SET assignee_id = MIN(assignee_id)` per task via a sub-select |
| 3 | `drop_column("tasks", "assignee_id")` | `drop_table("task_assignees")` |

### 2. Schemas and serializers - `backend/app/schemas.py`, `backend/app/serializers.py`

- `TaskCreate.assignee_ids: list[int] = []`;
- `TaskUpdate.assignee_ids: list[int] | None = None`
  (`None` = unchanged, `[]` = remove all assignees);
- `TaskSummaryOut.assignees: list[AssigneeOut]` - single `assignee_id` /
  `assignee` fields removed (breaking change, no external clients);
- `serialize_task` now serializes the whole collection.

### 3. Services - `backend/app/services/task_service.py`

- new helper `_set_assignees(db, task, assignee_ids, record=False)`:
  de-duplicates ids keeping the original order, resolves them to `Assignee`
  rows, raises `400 Assignee not found` for unknown ids, and optionally records
  a single `assignee_changed` history event with comma-joined names;
- `create_task` validates and applies `data.assignee_ids`;
- `update_task` applies `assignee_ids` only when the field is present;
- `move_inbox_to_backlog` now requires `task.assignees` instead of
  `task.assignee_id`.

### 4. Reports, intake, API - `report_service.py`, `telegram_intake_service.py`,
`api/tasks.py`, `api/assignees.py`

- PDF/Telegram reports print all assignees comma-joined (or `-`);
- Telegram intake no longer passes `assignee_id=None`;
- `GET /api/tasks?assignee_id=X` filters with
  `Task.assignees.any(Assignee.id == assignee_id)`;
- deleting an assignee that is still used by any task is blocked through the
  same `any(...)` query.

### 5. Frontend - `frontend/src`

- `types.ts`: `TaskSummary.assignees: Assignee[]`,
  `TaskCreatePayload.assignee_ids?: number[]`,
  `TaskUpdatePayload.assignee_ids?: number[]`;
- `components/ui.tsx`: new `assigneeLabel(assignees, fallback, max = 3)` helper
  that renders `"A, B, C +N"` (`max = 0` renders every name);
- `pages/TaskFormPage.tsx`: the assignee `<select>` is replaced by a checkbox
  list (`assigneeIds: number[]`), new `toggleAssignee`, no more
  "assignee is required" client-side guard;
- `TaskCard.tsx`, `BacklogPage.tsx` (table + search), `ArchivePage.tsx`,
  `TaskDetailPage.tsx` (all names, no truncation) use the helper;
- `styles.css`: `.checkbox-list` / `.checkbox-item` styles, sized checkbox that
  overrides the global `input { width: 100% }` rule;
- `translations.ts`: new `task.assignees` key (ru/en), table headers pluralized.

### 6. Spec - `spec.md`

- Inbox tasks "may temporarily have no assignees";
- Inbox -> Backlog requires a title and at least one assignee;
- "Existing Task Tracker Behavior" now lists "multiple assignees per task".

## Contract changes (breaking)

| Before | After |
|---|---|
| `TaskCreate.assignee_id: int` | `TaskCreate.assignee_ids: list[int] = []` |
| `TaskUpdate.assignee_id?: int \| null` | `TaskUpdate.assignee_ids?: list[int] \| null` |
| `TaskSummaryOut.assignee_id` / `assignee` | `TaskSummaryOut.assignees: list[AssigneeOut]` |

`GET /api/tasks?assignee_id=X` keeps its query parameter name and now matches
tasks where the assignee is one of several.

## Migrations

`backend/alembic/versions/0003_task_assignees.py` - contains a data migration
(existing `tasks.assignee_id` becomes one `task_assignees` row) and drops the
old column. Downgrade restores `assignee_id` from `MIN(assignee_id)`; extra
assignees are lost (documented limitation, no production data had more than
one).

## Verification

- `docker compose build backend && docker compose run --rm backend python -m pytest -q`
  -> `23 passed, 2 warnings`.
- Migration round-trip on a throwaway `postgres:16-alpine` database:
  - `alembic upgrade 0002`, seeded two tasks (one with assignee, one without);
  - `alembic upgrade head` -> `task_assignees: [(1, 1)]`, `tasks.assignee_id`
    columns: `0`;
  - `alembic downgrade 0002` ->
    `[('With assignee', 1), ('Without assignee', None)]`;
  - `alembic upgrade head` again - clean.
- `cd frontend; npm run build` (`tsc --noEmit && vite build`) -> EXIT=0,
  50 modules transformed.

## Known limitations

- Downgrade cannot restore more than one assignee per task (keeps the lowest id).
- History keeps a single `assignee_changed` event per update with comma-joined
  names, so the exact diff between two multi-assignee states is not itemized.
- The Inbox still requires at least one assignee before `Перевести в Backlog`.
