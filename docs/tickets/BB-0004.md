# BB-0004 - Structured Logging and Global Error Handling

## Status

Implemented

## Date

2026-11-04

## Problem

The backend had no logging and no exception handlers:

- there was not a single `import logging` in `backend/app`, so a failing
  request left no trace in `docker compose logs backend`;
- unhandled exceptions were formatted by Starlette itself, which answers with
  the plain-text body `Internal Server Error` and `text/plain` content type -
  the frontend tried to parse it as JSON and failed with an unrelated error;
- database failures (`SQLAlchemyError`) were indistinguishable from programming
  errors for the operator;
- nothing prevented a future log line from printing `DATABASE_URL` together
  with the database password.

## Goal

- one predictable log format for the application **and** for uvicorn, written
  to stdout, level controlled by the `LOG_LEVEL` environment variable;
- every unexpected failure produces a full traceback in the container log and
  a JSON `500` response with a safe message (no internals, no SQL, no DSN);
- `GET /api/health` keeps its contract, and a deliberately failing route
  exists to verify the whole chain end to end;
- no new dependencies.

## Changes

### 1. Logging - `backend/app/core/logging_config.py` (new), `backend/app/core/__init__.py` (new)

```python
LOG_FORMAT = "[%(asctime)s] %(levelname)s in %(module)s: %(message)s"
DATE_FORMAT = "%Y-%m-%d %H:%M:%S"
DEFAULT_LEVEL = "INFO"
```

- `setup_logging(level: str | None = None)` calls
  `logging.basicConfig(..., stream=sys.stdout, force=True)`;
  `force=True` makes the call idempotent (tests, reloads, repeated imports
  never duplicate handlers or lines);
- the level is taken from the argument, then `LOG_LEVEL`, then `INFO`; an
  unknown value silently falls back to `INFO` instead of raising;
- uvicorn installs its own handlers with its own format, so `uvicorn`,
  `uvicorn.error` and `uvicorn.access` get their handlers removed and
  `propagate = True`. This is an intentional deviation from uvicorn defaults:
  it is the only way to get `Application startup complete` in the project
  format;
- `redact_database_url()` is the only place that touches the DSN password and
  turns `postgresql://user:secret@host:5432/db` into
  `postgresql://user:***@host:5432/db` (port, path and query preserved).

### 2. API - `backend/app/api/health.py` (new), `backend/app/main.py`

The health route moved out of `main.py` into a router with
`prefix="/api/health"`:

| Method | Path | Behaviour |
|---|---|---|
| `GET` | `/api/health` | `200 {"status": "ok"}` (unchanged contract) |
| `GET` | `/api/health/error` | raises `ValueError("Test exception")` |

`main.py` now:

- calls `setup_logging()` **before** the app object is created, so every early
  message already uses the project format;
- creates `logger = logging.getLogger(__name__)` and logs the startup line
  with the redacted DSN:
  `Bwanabet Task Tracker starting, database=postgresql://user:***@host:5432/db`;
- registers `health.router` (inline `@app.get("/api/health")` removed);
- registers two exception handlers (Starlette picks the most specific class by
  MRO, so the database one wins for `SQLAlchemyError` subclasses):

| Exception | Status | Body | Log |
|---|---|---|---|
| `SQLAlchemyError` | `500` | `{"detail": "Database error occurred"}` | `logger.exception(...)` with traceback |
| `Exception` | `500` | `{"detail": "Internal Server Error. Please contact support."}` | `logger.exception(...)` with traceback |

`HTTPException` and `RequestValidationError` are left untouched, so the
existing `400`/`404`/`422` behaviour and messages did not change.


### 3. Tests - `backend/tests/test_error_handling.py` (new), `backend/tests/conftest.py`

New fixture `error_client`: same dependency override as `client`, but built as
`TestClient(app, raise_server_exceptions=False)`. Starlette's
`ServerErrorMiddleware` sends the `500` response and then **re-raises** the
exception, so a default `TestClient` would raise instead of returning the
response. The existing `client` fixture is untouched.

| Test | Asserts |
|---|---|
| `test_health_ok` | `/api/health` -> `200 {"status": "ok"}` |
| `test_unhandled_error_returns_json` | `/api/health/error` -> `500`, `application/json`, safe message |
| `test_unhandled_error_is_logged_with_traceback` | `caplog` has an `ERROR` record with `GET /api/health/error`, `ValueError: Test exception` and non-empty `exc_info` |
| `test_database_error_returns_safe_json` | `get_db` override raising `OperationalError` on `/api/assignees` -> `500 {"detail": "Database error occurred"}` + logged `OperationalError` |
| `test_database_url_is_redacted` | `redact_database_url()` unit test |
| `test_configured_database_url_password_is_not_redacted_to_plaintext` | password of the real `settings.database_url` disappears after redaction |
| `test_error_logs_do_not_contain_database_password` | an error request does not put the password into the log |
| `test_setup_logging_uses_single_stdout_handler_with_project_format` | exactly one root handler, `LOG_FORMAT` applied, level `INFO` |

### 4. Docs - `README.md`

New section `Logging and Error Handling`: format, `LOG_LEVEL`, both `500`
contracts, where to look for the traceback, DSN redaction, and the purpose of
`/api/health/error`.

## Contract changes

| Endpoint | Before | After |
|---|---|---|
| `GET /api/health` | `200 {"status":"ok"}` | unchanged |
| `GET /api/health/error` | `404` | `500` JSON |
| any unhandled error | `500 text/plain` body `Internal Server Error` | `500 application/json` with `{"detail": "..."}` |

Successful responses are byte-identical to before.

## Migrations

No schema changes: `0004` stays the head. Operationally one fix was needed on
the current Supabase database: the schema was already fully migrated (table
`roles` with 5 backfilled rows, `assignees.role_id` with its FK, old
`assignees.role` dropped) while `alembic_version` still contained `0003`
(a leftover from the previous verification session). Because of that the
container failed at boot with
`psycopg2.errors.DuplicateTable: relation "roles" already exists` and uvicorn
never started. Resolved without touching data by
`docker compose run --rm backend alembic stamp 0004`
(`alembic current` -> `0004 (head)`); `alembic upgrade head` is now a no-op and
the CI deploy will not repeat the failure.

## Known limitations

- Because Starlette's `ServerErrorMiddleware` re-raises after producing the
  response, uvicorn logs the same traceback a second time as
  `ERROR in h11_impl: Exception in ASGI application`. Two tracebacks per error
  are visible in the container log; this is a uvicorn/Starlette interaction,
  not a duplicated handler.
- `GET /api/health/error` is always registered (as specified), so it is
  reachable in production; it only raises a fixed exception and touches no
  data. Gate it behind an env flag if that ever becomes undesirable.
- Redaction covers only passwords embedded in the URL; a password passed
  separately or an ORM `repr` of a connection is not filtered.
- No request id / correlation, no JSON log output and no log shipping -
  stdout + `docker compose logs` only.
- Changing `LOG_LEVEL` requires a container restart: the value is read once,
  at import time of `app.main`.
- Error-handler tests must use the `error_client` fixture
  (`raise_server_exceptions=False`); the default `client` keeps raising and
  stays the right choice for ordinary endpoint tests.
