# BB-0005 - Basic Auth in Nginx (admin / bwana)

## Status

Implemented

## Date

2026-11-04

## Problem

The tracker was reachable by anyone who could open the URL: nginx served the
SPA from `/usr/share/nginx/html` and proxied `/api/` to FastAPI without any
authentication. For a single-user tool published on a public server that means
the board, the Telegram inbox and every mutating endpoint were open to the
whole internet.

## Goal

- one shared login and password for the whole tracker, requested by the browser;
- the password stored only as a hash in the repository, so it can be changed
  only through code (no plain text, no extra secret store);
- the static UI **and** the proxied API protected;
- no new dependencies, no backend changes, no schema changes.

## Changes

### 1. `frontend/.htpasswd` (new)

```text
admin:$apr1$S0meS4lt$l05Amgu.YaaO8tLrV8xb11
```

- Apache `apr1` (MD5) hash, one line, LF endings, no BOM, 44 bytes - verified
  with `od -c` inside the built image;
- the salt is part of the hash, so the value is deterministic for a given
  password: `openssl passwd -apr1 -salt S0meS4lt bwana` reproduces it byte for
  byte;
- **deviation from the ticket text:** the hash quoted in the task
  (`$apr1$S0meS4lt$q0Z2mI.4oG9P1z7y5X8wK.`) does not belong to the password
  `bwana`. Evidence: `openssl passwd -apr1 -salt S0meS4lt bwana` returns
  `$apr1$S0meS4lt$l05Amgu.YaaO8tLrV8xb11`, and a live `nginx:alpine` with the
  quoted hash answered `401` for `admin:bwana`. Because the acceptance
  criterion is admin / bwana opens the app, the verified hash with the same
  salt was committed (confirmed with the user).

### 2. `frontend/nginx.conf`

```nginx
    # One shared login for the tracker: covers the static UI and the /api/ proxy.
    auth_basic "Restricted Access";
    auth_basic_user_file /etc/nginx/.htpasswd;
```

- placed at `server` level instead of inside `location /` as the ticket
  suggested: `nginx.conf` has a separate `location /api/` with `proxy_pass`, so
  a `location /`-only directive would leave the API open, while
  `frontend/src/api.ts` calls it on the same origin (`BASE = ""`);
- the `server`-level value is inherited by both locations, so no duplicate
  directive is needed;
- the Telegram bot is unaffected: it uses long polling and talks to
  `http://backend:8000` directly, never through nginx.

### 3. `frontend/Dockerfile`

```dockerfile
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY .htpasswd /etc/nginx/.htpasswd
```

`.dockerignore` does not exclude `.htpasswd`, so the file reaches the final
nginx stage.

### 4. `.gitattributes` (new)

```text
frontend/.htpasswd -text
```

Marks the hash file as binary for git, so a Windows checkout with
`core.autocrlf=true` cannot add a CR that would become part of the hash and
silently break the login.

### 5. Documentation

`README.md` got an `Access Protection (Basic Auth)` section: the credentials,
why `/api/...` is covered too, how to rotate the password (new hash, then
rebuild the frontend) and the reminder that the file must keep LF endings.

## API and HTTP contract

| Request | Result |
|---|---|
| `GET /` without credentials | `401`, `WWW-Authenticate: Basic realm="Restricted Access"` |
| `GET /` with `admin:bwana` | `200`, `index.html` |
| `GET /` with a wrong password | `401` |
| `GET /board` (SPA deep link) with credentials | `200` (index.html fallback) |
| `GET /assets/*.js` with credentials | `200`; without credentials `401` |
| `GET /api/health` with credentials | `200 {"status":"ok"}` (BB-0004 contract) |
| `GET /api/health` without credentials | `401` - nginx answers, FastAPI is never reached |

## Verification

- `docker compose build frontend` - image rebuilt, step `COPY .htpasswd` applied;
- `docker compose up -d` - frontend container recreated, `nginx -t` reports that
  the configuration file syntax is ok;
- curl matrix against `http://localhost:5173` (see the table above): no creds
  gives `401`, `admin:bwana` gives `200`, `admin:wrong` gives `401`,
  `admin:bwana /board` gives `200`, `/api/health` with creds gives `200
  {"status":"ok"}`, `/api/health` without creds gives `401`,
  `/assets/index-*.js` gives `200` with creds and `401` without, and the 401
  response carries `WWW-Authenticate: Basic realm="Restricted Access"`;
- `docker compose exec frontend cat /etc/nginx/.htpasswd` returns the repository
  line unchanged (checked with `od -c`: no CR, no BOM);
- platform check: an isolated `nginx:alpine` container on port 8099 with a
  matching apr1 hash answered `admin:bwana` with `200`, which proves that
  Alpine/musl verifies apr1 correctly and the original `401` came from the
  hash, not from the base image.

## Known limitations

- One shared account: no per-user accounts and no logout button. The browser
  keeps the credentials until it is closed or the password changes.
- A password change takes effect only after the frontend image is rebuilt and
  the container is recreated (`docker compose up -d --build frontend`).
- `docker-compose.yml` still publishes `8000:8000`, so the API answers directly
  when that port is reachable on the server. Basic Auth covers only the nginx
  entry point; close the port in the firewall if the API must not be reachable
  without the password.
- Basic Auth sends credentials base64-encoded, so HTTPS on the public server is
  required, otherwise the password travels in clear text.
- `.htpasswd` must keep LF endings: a Windows checkout with
  `core.autocrlf=true` would add a CR to the hash and break the login. The file
  is currently byte-identical inside the image.
- The Telegram bot bypasses nginx (long polling to `backend:8000`), so it keeps
  working without the login - by design.
